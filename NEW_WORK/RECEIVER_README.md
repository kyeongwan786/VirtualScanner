# NEW_WORK Receiver V4

이 Receiver는 중앙 OCR V3의 선택 PC 전송을 받는다. 중앙 OCR V1은 실행 PC에 직접
SK/KT 결과를 적용하므로 Receiver가 필요하지 않다.

NEW_WORK central and Receiver use the `KyeongwanReceiver` HTTPS relay. The central PC sends the manifest and normalized JPG pages directly, with reviewed portal metadata. Receiver atomically claims and downloads up to four independent jobs concurrently; pages inside each job can also download up to four at once. It validates each JPG, stores it locally, then acknowledges receipt. This avoids creating, uploading, downloading, and extracting a ZIP. It does not write SK/KT portal data on arrival: the operator reviews the identity type and presses **신분증 확인** in Receiver first. Documents-only packages are acknowledged after local storage and never change SK/KT identity data. It does not require an SMB share or an inbound port on the intake PC.

The sender keeps the two input roles separate from file format. The identity area accepts JPG/JPEG/PNG or PDF and normalizes the selected identity image to JPG before identity OCR. For an identity PDF, only its first page is used as the identity image; remaining pages are not added to the document queue. Add documents separately in the document area. The document area accepts PDF/JPG/JPEG/PNG; PDFs become one scanner JPG per page and image files become one scanner JPG page each. These normalized pages use the same Receiver and TWAIN queue contract.

The sender pre-populates its 17 destination rows with Relay station IDs. A populated ID means a job can be routed to that station; it does not mean a Receiver is installed or online. Sender status cards query the Relay's authenticated Receiver-presence endpoint and show online, offline, unregistered, or an unknown status. Use **상태 새로고침** to request an immediate update. The Relay must advertise `station-presence-v1`; if the endpoint returns 404, the UI identifies the missing status API, marks station status as unknown, and stops polling until manually refreshed. Job uploads use a separate endpoint and can still work.

## Relay service

The deployed Render service is `https://kyeongwan-relay-test.onrender.com`. Its `/health` endpoint reports the relay features. The service uses HTTPS (TCP underneath); central and Receiver PCs make outbound connections, so no inbound port forwarding is needed.

Render settings must contain:

- `KYEONGWAN_RELAY_CENTRAL_TOKEN`: a random token at least 32 characters long.
- `KYEONGWAN_RELAY_STATIONS`: a JSON array with each exact `station_id` and its unique random token, for example `[ {"station_id":"desk-01","token":"a-long-random-station-token"} ]`.
- `KYEONGWAN_RELAY_DATA_KEY`: a Fernet key generated by Render or provisioned securely.

The relay encrypts queued JPG pages at rest and removes their payload after Receiver acknowledges local receipt. The Relay must advertise `new-work-claim-v1`. Claim leases prevent multiple Receiver workers from downloading the same job. An abandoned claim expires after five minutes. The older ZIP protocol remains supported for compatibility.

With `new-work-inbox-v1`, Receiver checks for JPG and ZIP jobs in a single request. It checks every 500 ms while idle, then adds up to three workers when it claims a job. Each locally saved and acknowledged job appears in **받은 자료함** as it finishes. Single-page jobs reuse the current HTTPS connection for page transfer when the relay keeps it open. For these changes, deploy the Relay with the updated `relay-requirements.txt` and build the V3 Sender and Receiver from the updated source. An older Relay that advertises `new-work-claim-v1` uses the separate JPG and ZIP checks.

The three-second target covers the interval from pressing Send with files ready to the job appearing in **받은 자료함**. For a batch, record when the first job appears and when the last job appears. Measure on the Windows workstations with non-sensitive sample JPGs and PDFs, covering single-page, multi-page, and batch sends. Record the total JPG bytes alongside the delivery time. Relay startup and the time needed to upload and download the bytes limit achievable delivery times.

Emergency locks, station provisioning hashes, and cleanup receipts use the `DATABASE_URL` PostgreSQL connection and survive Render restarts. Set `DATABASE_URL` in the Render service environment to the pooled Neon connection string. Encrypted queued job payloads still use Render's temporary `/tmp` storage, so queued transfers can be lost on a restart; use this free setup for controlled tests only until durable payload storage is added. `/health` reports `emergency_storage_persistent: true` only while Neon is reachable. Keep the existing Fernet key stable across deploys so queued encrypted data remains readable.

The Sender's Receiver status cards use authenticated `GET /v1/stations/status` (central token). Each Receiver's existing two-second emergency-command poll updates an in-memory last-seen timestamp; the Sender reports online when the latest poll is within 15 seconds, otherwise offline. A newly provisioned station with no recent poll appears offline. The timestamp is intentionally volatile and resets when Relay restarts. Deploy the Relay with `station-presence-v1` and rebuild/update the Sender to show live status. A 404 means the currently deployed Relay does not have the status route; redeploy the latest Relay code, then retry **상태 새로고침**. This does not prevent uploads through the separate job endpoint. The Receiver's “Relay 설정됨” label confirms saved settings only; the Sender's status card is the live reachability check.

When a Receiver later reconnects, it applies the active emergency command, records cleanup success or errors, and requests shutdown. Offline stations remain `pending`. The receipt reports cleanup and a shutdown request; it cannot prove that the remote operating system actually terminated the process. On the central PC, with the Sender's saved Relay configuration available, inspect the current per-station results with `cd NEW_WORK && python -m new_work.emergency_status`.

## Automatic client settings

To avoid typing the Relay URL and tokens on each PC, prepare one private `relay-provisioning.json`
with the Render URL, central token, and every station ID/token. The schema is shown in
`relay-provisioning.example.json`. Keep the private file out of Git and the source ZIPs. For a
Windows source ZIP build, copy it into the extracted `NEW_WORK` folder before building. The build
script finds the same file beside `KyeongwanReceiver` when building from a full repository checkout.
The Render environment variables still need to be configured once by the service administrator and
must match this file; the desktop app does not change Render dashboard secrets.
The Sender package embeds the central token and every station token so it can provision all seats
automatically. The Receiver package embeds every station token so an operator can select the local
seat and save settings without entering secrets. Anyone who obtains either package may extract
these embedded credentials. In
Receiver settings, choose the PC's station and press **자리 설정 적용**. In the Sender, pressing
**Relay 설정** loads and saves the central settings automatically. If no private provisioning file
was supplied, both apps keep the manual settings flow.

## Configure the central PC

1. Start the NEW_WORK central app and choose **Relay 서버**.
2. Enter the Render HTTPS origin, such as `https://kyeongwan-relay-test.onrender.com`, and the central token. The app stores this in the current user's NEW_WORK settings.
3. Open **접점 설정** for each workstation and enter its exact Render `station_id` in **Render Relay 자리 ID**. This value must match both Render's station list and that workstation's Receiver setting.
4. Select a workstation, add an identity JPG, PDFs, or both, then choose **선택 PC로 저장**. OCR and PDF conversion finish before the package uploads. The sender reports success when Receiver safely stores the package; for an identity, the operator must still press **신분증 확인** on Receiver to write SK/KT portal data. If it times out after upload, do not resend the same intake until Receiver status is checked.

In Receiver's received-folder document preview, use **이 페이지만 제외** to remove one JPG page from a multi-page PDF before queueing that document for scanning. The other pages stay in the same document and keep their order. The excluded JPG goes to the Receiver work-folder trash and can be restored with **Ctrl+Z**. If the document is already in the scan queue, cancel it back to the waiting list first; a page already scanned cannot be recalled. To remove every page, use the document's delete action.

In the central identity preview, drag the blue `idCrop`/`CR.jpg` box to move it. Its size is fixed for the selected identity type and cannot be resized. Drag outside the box to place the same fixed-size region at a new position. **자동 영역 복원** returns to the detected crop. The exact visible source-image coordinates, including an automatic fallback box and batch-send items, travel with the work package; Receiver must use those coordinates rather than independently estimating the box. Central SK generation uses them for the Base64 `idCrop`, and Receiver KT generation uses them for `CR.jpg`. The normal portal output dimensions are retained. Receiver PCs must run a build containing the crop-coordinate support for manual KT regions to take effect.

## Start and configure a workstation Receiver

On the Windows intake PC, run from a Windows checkout of this repository:

```powershell
cd C:\path\to\VirtualScanner\NEW_WORK
python -m pip install -r requirements_receiver.txt
python .\receiver_run.py
```

For a standalone Receiver app without the central OCR dependencies, use the Receiver-specific build files on Windows:

```powershell
.\build_receiver_windows_v4.bat
```

The package is also available through `NEW_WORK-Receiver-V4-Windows-Build.zip`. Run `dist\new_work_receiver_v4\new_work_receiver_v4.exe`. If built with the private provisioning file, in **Receiver 설정** select the matching station and press **자리 설정 적용**. Otherwise enter:

- Render Relay HTTPS address.
- `station_id` exactly as configured in Render and the central workstation entry.
- This station's unique token from `KYEONGWAN_RELAY_STATIONS`.
- This PC's local `sk_report.txt`, `myCustomer.db`, KT image folder, and virtual scanner `ready` folder.
- A local Receiver work folder for retained jobs and backups.

Receiver checks for new work every second when the GUI is open. During download, it shows progress, rate, and estimated remaining time. Keep Receiver running while the central PC sends work. Acknowledgement means the complete job was verified and saved locally; it does not mean that SK/KT was updated. Newly received identities are automatically saved to the selected SK/KT portal before acknowledgement. If portal saving fails, the received job is retained with a visible error for correction/retry; receipt acknowledgement alone is not proof of portal-save success.

**받은 자료 초기화** clears this Receiver's local received job packages, including identity JPGs, OCR values, PDF page JPGs, manifests, the saved scan/wait/completed lists, in-memory previews, and all job contents of the configured scanner `ready` folder. It can be confirmed while scanning or receiving. An in-flight Relay receive is cancelled before cleanup. A scan may fail when its `ready` files are removed. It does not delete already-applied SK/KT target files or their backups, or jobs still waiting at Relay. The confirmation dialog shows the `ready` path and deletion scope.

Receiving another package adds another folder and keeps existing received folders and scanner queues. This lets staff sort multiple intake requests independently. Use **받은 자료 초기화** only when you intend to delete retained folders and scanner `ready` contents; the confirmation dialog lists the paths and deletion scope.

## Receiver screen and local PDF scan queue

송신기의 **긴급 중단**에서 `전체 폐기`를 확정하면 Relay가 잠기고 대기 중인 모든 작업이
삭제됩니다. 실행 중인 최신 V3 Receiver는 Relay 명령을 확인해 NEW_WORK로 받은 작업자료와
이 Receiver가 `ready`에 올린 파일, Windows Receiver 설치 폴더를 삭제하고 종료합니다.
기존 SK/KT 결과와 데이터베이스, 백업, 설정은 보존합니다. 오프라인 PC는 재연결 또는 다음 실행 때 처리됩니다. 이전 버전은
자체 삭제 명령을 처리하지 않으므로 Receiver를 갱신해야 합니다. Render 운영 로그와
저장소 원본 코드는 이 기능의 삭제 대상이 아닙니다. 긴급 잠금은 Render `DATABASE_URL`
Neon DB에 저장되며, `/health`의 `emergency_storage_persistent`가 `true`인지 확인하세요.

The Receiver opens one HTML/CSS dashboard with received folders on the left and the selected folder on the right. New identities are saved automatically: SK writes the configured `sk_report.txt`; KT updates the configured database and generates `ORG.jpg` and `CR.jpg`. Existing backups remain enabled. The screen shows the portal and save state; a failed save remains available for correction or retry. **수정하기** lets the operator change OCR values, crop and SK/KT even after saving. Portal-specific applied markers retain the KT row ID when switching back. Saving to another portal does not undo the earlier portal output. Identity-only and identity-plus-documents use the same automatic save path; document-only jobs do not write portal data. Parallel reception and local/received corrections serialize portal writes.

The Receiver also has an **이 PC에서 직접 접수** tab for busy periods when staff should not walk to the central PC. Choose a JPG/PNG identity and/or one or more PDFs; identity OCR and PDF-to-JPG conversion run locally as soon as each file is added. OCR fields and the fixed-size, identity-type-specific `idCrop` box can be reviewed on that page. Choose SK or KT, then register the prepared material in the same received-folder list. Use **신분증 저장** to save directly to the selected portal; SK/KT may be changed and saved again after editing. Registering prepared material in the received list retains its selected-portal save state. Converted document groups can be added to the scanner queue independently. Local work does not require Relay settings. The OCR engine and its PP-OCRv5 model weights are included in the Receiver build, so that build is larger and needs the same supported Paddle runtime as the central OCR app.

The sender converts PDFs to JPG pages before transfer; Receiver stores and scans those JPGs. Each original PDF is kept as a grouping label, while the row displays the converted JPG page thumbnails and count. Click a thumbnail to page through the images. A new image group starts waiting. Press **스캔 대기열에 추가** to copy only that group's pages to `ready`; its status changes to **스캔 대기 중** and the button becomes **스캔 취소**. Cancel moves it back to waiting and removes only its staged copy from `ready`. If TWAIN is already acquiring that group, the current scan may fail. Completed groups show **스캔 완료**.

Select folders in either list and press **Delete**, or use **선택 서류 삭제**. The Receiver moves their page folders into a local per-job trash folder and removes them from both lists. Press **Ctrl+Z** or **삭제 취소** to restore the most recent deletion; the undo history survives a Receiver restart. Documents currently being scanned cannot be deleted. **서류 목록 초기화** permanently removes listed and trashed document pages and clears the undo history.

**서류 목록 초기화** asks for confirmation, blocks while the scanner `ready` folder has a job, then permanently deletes PDF page JPGs (including trashed pages) and clears those PDF entries from their local manifests. It keeps identity images, OCR values, SK report files, KT databases, and the scanner folder. This reset cannot be undone.

Folder names are normalized for display so Korean filenames created on macOS do not appear as separated consonants and vowels in the Windows Receiver.

The Receiver UI uses HTML/CSS in a pywebview desktop window and can also run on macOS from source with `NEW_WORK/run_receiver_macos.command`, or be packaged as a Mac app with `NEW_WORK/build_receiver_macos.command`. Both use the same folder dashboard for Relay receipt, identity confirmation, page preview, and local queue management. TWAIN acquisition is Windows-specific and must be used on a Windows workstation for actual business-page scanning.

Identity images, reviewed OCR values, received job folders, previous SK reports, KT database backups, and scanner queue data remain on the workstations until explicitly reset or normally completed. The Render relay is a separate cloud copy: its page payload is deleted after Receiver confirms local receipt, while a small status record remains so the central app can confirm delivery.

## V4 화면 확인

창 제목은 `접수 자료함 · Receiver V4`, 화면 상단은 `접수 자료함 · V4`입니다. 신분증만 또는 신분증+서류 접수의 목록 왼쪽에는 해당 신분증의 실제 썸네일을 76×50px 안에 비율을 유지해 표시합니다. 서류만 접수는 문서 아이콘을 유지합니다. 기존 V3 EXE는 자동 갱신되지 않으므로 V4를 새로 빌드하고 실행해야 합니다. 기존 자리 설정과 받은 자료 경로는 유지합니다. 같은 자리의 V3와 V4를 동시에 실행하지 마세요. V4 Windows 빌드 및 실제 수신 화면 확인은 미실행입니다.

## 로컬 접수의 저장 포탈 변경

`이 PC에서 직접 접수`에서는 저장 후에도 SK/KT를 전환하여 같은 신분증을 선택한 포탈에 저장할 수 있습니다. 저장 요청에 선택한 포탈을 명시하며, 기존 백업은 유지하되 저장 전 확인 모달은 표시하지 않습니다. `applied.json`의 `by_carrier`에 포탈별 기록과 KT 행 ID를 보관합니다. 다른 포탈 저장이 실패해도 기존 성공 기록은 유지합니다. 받은 자료함 등록 시에는 현재 선택한 포탈의 성공 기록만 적용 완료로 취급합니다. 이전 포탈 저장은 자동으로 취소되지 않습니다. Windows에서 반복 전환/저장 확인은 아직 수행하지 않았습니다.

## Windows 자동 시작

빌드된 new_work_receiver_v4.exe를 사용할 Windows 계정으로 한 번 실행하면 자동 시작을 등록합니다.
등록 위치: HKCU\Software\Microsoft\Windows\CurrentVersion\Run 의 NewWorkReceiverV4.
관리자 권한은 필요하지 않습니다. PC 전원을 켠 뒤 해당 사용자가 Windows에 로그인하면 Receiver가 실행됩니다.
로그인 전 실행하는 서비스는 아닙니다. EXE와 _internal 등 배포 폴더 전체를 같은 위치에 유지하세요.
폴더를 옮겼다면 새 위치의 EXE를 한 번 실행하여 등록 경로를 갱신하세요.
자동 실행과 수동 실행이 겹치면 같은 Windows 세션의 V4는 한 개만 실행합니다.
자동 시작을 끄려면 Windows 작업 관리자의 시작 앱에서 수신기를 사용 안 함으로 설정하세요.
기존 긴급 중단 흐름에서는 이 자동 시작 등록도 제거합니다.
Python 소스 실행 및 macOS 실행은 Windows 자동 시작에 등록하지 않습니다.
Windows 재로그인/자동 실행 검증은 아직 수행하지 않았습니다.

수신기 웹 화면의 저장 확인·작업 초기화·삭제 안내는 해당 창 내부 모달로 표시합니다. 별도 Tk/브라우저 확인창을 사용하지 않습니다. Windows 실제 표시 동작은 대상 PC에서 확인해야 합니다.

받은 자료 화면 오른쪽 신분증 미리보기는 기본 160px(높이가 작은 화면은 130px)로 표시합니다. 신분증 접기/펼치기로 서류 목록 공간을 확보할 수 있으며, 수정하기를 누르면 펼쳐집니다. 신분증 수정 영역은 내부 스크롤을 사용하여 서류 목록 높이를 확보합니다.

수신 자동 저장과 받은 자료의 SK↔KT 수정 전환은 코드 반영 상태입니다. Windows의 실제 SK report/KT DB·이미지 저장과 반복 수정 동작은 아직 검증하지 않았습니다. 송신기 V3는 주민번호 검증 실패만으로 전송을 막지 않으며, OCR 결과와 신분증 종류 준비가 끝나면 별도 검토 확인 없이 전송할 수 있습니다. OCR 엔진 실패나 신분증 종류 미확정은 계속 표시합니다.
